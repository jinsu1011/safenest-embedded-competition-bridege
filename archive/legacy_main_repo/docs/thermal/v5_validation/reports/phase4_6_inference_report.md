# Phase 4~6: 시각화 및 실기기 TFLite 추론 보고서

## 1. 개요
* **목적**: 실기기에서 파싱된 `float32` 프레임을 바탕으로 터미널 시각화를 구현하고, V5 INT8 TFLite 모델(`thermal_fall_int8_v0.1.0.tflite`)에 직접 입력하여 실시간 추론 성능과 안정성을 검증.
* **진행 시간**: 2026-08-11

## 2. Phase 4: 실시간 열화상 시각화 결과
- **구현 방식**: 20.0°C ~ 35.0°C를 10단계의 ASCII 문자로 매핑하여 터미널에 실시간(15x40 크기로 축소) 출력.
- **검증**: 사람의 이동이나 열원 유무에 따라 실시간으로 화면이 갱신되며, 프레임 지연 없이 원활한 시각화가 이루어짐을 증명.

## 3. Phase 5~6: 실기기 TFLite 추론 검증
- **모델 사양**: `thermal_fall_int8 (v0.1.0)`, INT8 Quantized.
- **추론 결과 (프레임 1~26)**:
  - 사람이 없는 상태에서 `NOT_HUMAN (Index: 0)` 100.0% Confidence 산출 확인.
  - 합성(Mock) 데이터가 아닌, **실제 하드웨어 Raw 프레임**을 기반으로 에러(`fallback_used`) 없이 Inference 성공.
- **지연시간(Latency)**: 라즈베리파이 5 CPU 기준 **0.3ms ~ 3.7ms**의 극초저지연(Latency) 기록. (매우 우수)

## 4. ⚠️ 중대 결함 발견: 프레임 27 하드웨어 Crash (Brownout)
- **증상**: 27번째 프레임에서 최고 온도가 **655.3°C (0xFFFF)**로 스파이크 발생 직후, 라즈베리파이와의 TCP 연결이 강제 종료(`Connection closed`)됨.
- **원인 분석**: 
  - `655.3`은 16비트 최대값(65535/100)으로, 열화상 센서의 SPI MISO 통신선이 응답하지 않아 쓰레기값이 읽힘을 의미함.
  - 직후 끊어짐 현상은 ESP32가 자체 재부팅되었음을 뜻하며, 이는 Wi-Fi 송신과 센서 샘플링이 겹치면서 3.3V 레귤레이터의 전류 한계를 초과하여 전압 강하(Brownout)가 발생했기 때문으로 판단됨. (트러블슈팅로그 7번 항목에 상세 기록)

## 5. 결론
* **판정**: **소프트웨어 파이프라인 PASS / 하드웨어 안정성 FAIL**
* 모델 추론 및 시각화 등 온디바이스 AI 파이프라인 자체는 100% 정상 작동함을 입증하였으나, 연속 구동 시 ESP32 하드웨어 전원부 안정화 작업(캐패시터 추가 등)이 필수적으로 요구됨.
