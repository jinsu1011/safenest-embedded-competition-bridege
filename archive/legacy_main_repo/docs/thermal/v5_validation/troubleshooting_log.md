# SafeNest 프로젝트 트러블슈팅 로그

본 문서는 SafeNest 센서 통합 시스템(열화상, SCD40, PIR)을 개발 및 테스트하는 과정에서 발생했던 문제점들과 그 해결책을 시간순/유형별로 기록한 로그입니다. 향후 유사한 에러 발생 시 빠르게 대처하기 위해 작성되었습니다.

---

## 📌 1. ESP32-C6 (Native USB) 시리얼 모니터 먹통 현상

* **증상**: 코드가 100% 정상적으로 업로드(`Hash of data verified`) 되었고 `Hard resetting via RTS pin...` 메시지까지 떴으나, 시리얼 모니터에 아무런 출력이 나오지 않음.
* **원인**: 코드 내의 `while (!Serial);` 무한 루프. ESP32-C6와 같은 네이티브 USB(USB-Serial/JTAG) 기반 보드는, IDE에서 USB CDC 설정이 꺼져있거나 시리얼 모니터가 늦게 열릴 경우 저 코드 구간에 갇혀 다음 단계(`setup()` 이후)로 넘어가지 못하는 고질적인 버그가 있음.
* **해결책**:
  1. **코드 수정 (권장)**: `while (!Serial);`을 삭제하고, 대신 `delay(2000);`을 넣어 부팅 안정화 시간만 확보.
  2. **IDE 설정 변경**: 아두이노 IDE 툴(Tools) 메뉴에서 `USB CDC On Boot` 옵션을 `Enabled`로 변경하여 USB가 기본 시리얼 통신구가 되도록 강제.

## 📌 2. PIR 센서 모션 미감지 및 플로팅(Floating) 이슈

* **증상**: 센서 앞을 움직여도 감지 로그가 안 뜸. 반면, 데이터 핀(D6)을 점퍼선에서 빼서 공중에 띄우면 미친 듯이 감지 로그가 도배됨.
* **원인 분석**:
  1. 핀을 뺐을 때 로그가 뜬다는 것은 ESP32의 하드웨어 인터럽트(RISING) 코드는 완벽하게 동작 중이라는 의미(플로팅 노이즈에 반응).
  2. 핀을 연결했을 때 안 되는 것은 PIR 센서가 계속 0V(LOW) 신호만 뿜고 있기 때문.
* **최종 원인 및 해결책**:
  1. **ESP32 내부 저항 간섭**: `pinMode(PIN_PIR, INPUT_PULLDOWN);`으로 설정했으나, 내부 풀다운 저항이 PIR의 약한 HIGH 신호를 이겨버리고 0V로 끌어내리는 현상 발생. 👉 `pinMode(PIN_PIR, INPUT);`으로 수정하여 해결.
  2. **동작 전압(VCC) 부족**: 가장 흔한 실수. HC-SR501 PIR 센서는 5V 전원이 필수적임. ESP32의 3.3V 핀에 꽂으면 켜지긴 하지만 적외선 감지 로직이 동작하지 않아 계속 LOW만 출력함. 👉 센서의 VCC 선을 3.3V에서 **5V(VIN/VBUS) 핀**으로 옮겨 꽂아 해결.

## 📌 3. SCD40 센서 라이브러리 컴파일 에러 (대소문자 구분)

* **에러 로그**: `fatal error: SensirionI2CScd4x.h: No such file or directory`
* **원인**: 라이브러리는 정상적으로 설치되었으나, 윈도우 기반 아두이노 빌드 시스템이 C++ 헤더 파일의 대소문자를 엄격하게 구분함. 코드에는 `SensirionI2CScd4x.h` (대문자 C)로 적혀있었으나, 실제 설치된 공식 라이브러리 파일명은 `SensirionI2cScd4x.h` (소문자 c)였음.
* **해결책**: 
  * `#include <SensirionI2CScd4x.h>` 👉 `#include <SensirionI2cScd4x.h>` 로 수정.
  * 클래스 객체 선언부 `SensirionI2CScd4x scd4x;` 👉 `SensirionI2cScd4x scd4x;` 로 수정.

## 📌 4. SCD40 라이브러리 v2.0 API 변경에 따른 컴파일 에러

* **에러 로그**:
  * `no matching function for call to 'SensirionI2cScd4x::begin(TwoWire&)'`
  * `no matching function for call to '...getSerialNumber(uint16_t&, uint16_t&, uint16_t&)'`
  * `'class SensirionI2cScd4x' has no member named 'getDataReadyFlag'`
* **원인**: Sensirion 공식 라이브러리가 최신 버전(2.0)으로 메이저 업데이트되면서 함수 인자와 이름(API)이 하위 호환성 없이 대폭 변경됨.
* **해결책 (최신 API 문법으로 코드 전면 수정)**:
  1. I2C 초기화: `scd4x.begin(Wire);` 👉 `scd4x.begin(Wire, 0x62);` (주소 0x62 명시 필수)
  2. 시리얼 넘버: 16비트 변수 3개 대신, 64비트 변수(`uint64_t`) 1개를 받도록 수정.
  3. 데이터 레디 플래그: `getDataReadyFlag()` 👉 `getDataReadyStatus()` 로 함수명 변경.

## 📌 5. ESP32 브레드보드 전원 분배와 Brownout(무한 재부팅) 방어

* **이슈 배경**: 노트북 USB 전원을 이용해 ESP32와 3개의 센서를 브레드보드로 구동하려 할 때, 전력 부족 및 보드 다운(Brownout) 현상 우려.
* **원인**: 
  * ESP32(특히 XIAO 보드) 내부에 있는 3.3V 변환 레귤레이터(LDO)는 처리할 수 있는 한계 전류가 400mA 수준으로 매우 낮음.
  * Wi-Fi 송신(최대 400mA) + 열화상 카메라 + SCD40(측정 시 200mA)가 동시에 작동하면 전류 한계를 초과해 3.3V 전압이 뚝 떨어지며 ESP32가 스스로 재부팅됨.
* **해결책 (배선 전략 도입)**:
  1. 전력을 많이 먹는 센서(PIR 등 5V 지원 기기)는 ESP32의 3.3V 핀(레귤레이터 통과)이 아닌, **5V 핀(노트북 직결 바이패스)**에 물려 LDO의 부담을 덜어냄.
  2. **ESP32-WROOM-32 보드 적용 시**: WROOM-32는 LDO 용량이 약 800mA로 넉넉함. 따라서 통신 안전을 최우선으로 하여, 5V 인가 시 I2C/SPI 통신 전압까지 5V로 뛰어올라 ESP32 GPIO 핀(3.3V 한계)을 망가뜨릴 위험이 있는 SCD40과 열화상 카메라는 **3.3V 레일**에 안정적으로 물리도록 매뉴얼화. (단, PIR은 무조건 5V 필수)

## 📌 6. 열화상 센서 데이터 송수신 프로토콜 변경 (UDP ➔ TCP) 및 Trade-off

* **이슈 배경**: 초기 열화상 카메라 스트리밍은 지연을 최소화하기 위해 UDP 프로토콜을 사용했으나, 네트워크 MTU(최대 전송 단위) 한계로 인해 패킷이 쪼개지고 무선망에서 조각 하나만 유실되어도 전체 프레임이 심각하게 깨지는(Tearing) 현상이 발생함.
* **원인 및 Trade-off 분석**:
  * **UDP (기존)**: 오버헤드가 적어 전송 지연시간(Latency) 측면에서는 유리하나, 데이터 도달을 보장하지 않아 패킷 유실 시 에러 처리가 매우 복잡하고 화질 열화가 심각함. (빠름 ↔ 신뢰성 낮음)
  * **TCP (변경 후)**: 3-Way Handshake 및 패킷 재전송 등 오류 제어 로직으로 인해 헤더 오버헤드가 증가하고 지연시간이 길어질 수 있으나, 수신 측에 바이트 스트림이 100% 완벽한 순서로 도착함을 보장함. (신뢰성 높음 ↔ 오버헤드 증가)
* **해결책 및 결론**: SafeNest 시스템은 단순 영상 감상이 아닌 '위험 판정을 위한 정확한 온도 데이터'가 필수적인 도메인 특성을 가짐. 따라서 0.1초의 지연시간 손해를 감수하더라도 완벽한 신뢰성을 보장하는 **TCP 통신(포트 9000, SNST 통합 프로토콜 적용)**으로 전면 전환. 이를 통해 10,080바이트의 대용량 열화상 프레임도 유실 없이 안정적으로 스트리밍하는 데 성공.

## 📌 7. 열화상 센서 연속 수신 중 655.3°C (0xFFFF) 스파이크 및 연결 끊김 (Brownout 의심)

* **증상**: TCP 망을 통해 26프레임까지 정상적인 온도(27~30°C)가 수신되다가, 27프레임 즈음 갑자기 프레임 내 최고 온도가 **655.3°C**로 치솟고 직후 Connection closed 에러와 함께 연결이 완전히 끊어짐.
* **원인 분석**:
  1. 655.3°C는 16비트 최대값인 65535 (0xFFFF)를 100으로 나눈 값임. 이는 센서 통신(SPI) 시 MISO 핀이 High 상태로 고정되어 쓰레기값을 읽어왔음을 의미.
  2. 직후 TCP가 끊어졌다는 것은 ESP32가 재부팅되었음을 강력하게 시사함.
  3. 다른 센서들의 전원을 분리했음에도, Wi-Fi 데이터 전송 스트레스 + 열화상 센서의 연속 샘플링 전력 소모가 겹치는 순간 ESP32 3.3V LDO 레귤레이터의 전류 한계를 초과하여 전압 강하(Voltage Drop)가 발생, 센서 통신이 먼저 뻗고 ESP32가 리셋된 것(Brownout)으로 판단됨.
* **해결책 및 권장사항**:
  * 테스트 과정에서는 센서들의 전원을 분리하여 부하를 최대한 줄일 것.
  * 실서비스 보드(PCB) 구성 시, ESP32의 3.3V 핀에만 의존하지 말고 외부 전원 분배 회로나 디커플링 캐패시터를 보강하여 순간적인 전압 강하를 방어해야 함.

## 📌 8. UDP 통신 시 Wi-Fi MTU 한계로 인한 패킷 드랍 (WAITING_FOR_FIRST_FRAME 지속 에러)

* **증상**: XIAO-ESP32C6에서 10,080바이트의 UDP 패킷을 성공적으로 전송(Frame sent via UDP)했다고 시리얼 모니터에 출력되나, 라즈베리파이의 파이썬 스크립트에서는 단 1바이트도 수신하지 못하고 2초마다 WAITING_FOR_FIRST_FRAME 타임아웃 에러를 뱉음.
* **원인 분석**:
  1. 단일 UDP 패킷에 10KB(10,080 bytes)의 거대한 페이로드를 담아 전송하면, 일반적인 Wi-Fi 공유기(MTU 1500)에서 IP 단편화(Fragmentation)가 발생함.
  2. 무선 네트워크(Wi-Fi) 환경에서는 단편화된 조각 중 단 하나라도 유실되면 OS(라즈베리파이) 단에서 10KB 전체 패킷을 폐기(Drop)해버림.
* **해결책 및 권장사항**:
  * ESP32 송신부(udp_sender_esp32.ino)에서 데이터를 공유기가 안전하게 소화할 수 있는 **1440바이트 단위로 쪼개서(Chunking)** 7번 전송하도록 로직 수정.
  * 수신부(step4_udp_scenario_tester.py)에서는 1440바이트 패킷들이 도착할 때마다 버퍼에 차곡차곡 쌓아(Accumulate), 총 10,080바이트가 완성되었을 때만 파서(Parser)로 넘기도록 버퍼링(While 루프) 로직 보완. 이를 통해 패킷 유실률을 획기적으로 낮추고 안정적인 수신 달성.
