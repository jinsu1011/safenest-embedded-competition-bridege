## 0. 결론부터

**현재 이 보고서는 "잘 쓴 보고서"다. 그러나 아직 "대상 보고서"는 아니다.**

두 가지는 다른 물건이다.

- 잘 쓴 보고서 = 한 일을 정확하게, 과장 없이, 읽기 쉽게 전달한다. **지금 여기까지는 왔다.**
- 대상 보고서 = 위에 더해, **심사위원이 심사장을 나가서도 한 문장으로 기억하는 결과 하나**를 갖는다.

지금 보고서에는 그 한 문장이 없다. 정확히 말하면, 그 문장이 들어갈 자리가 비어 있다.

| 예상 점수 | 상태 |
|---|---:|
| 문체·레이아웃 개선 전 (적대적 심사) | 70 |
| **현재 (2026-08-24 버전)** | **76 ~ 80** |
| 4센서 통합 HIL + 경보 지연 실측 반영 시 | 84 ~ 88 |
| + AI 검증 1건 추가 + 전력·복구 실측 + 원가 | **89 ~ 93** |

**대상 커트라인은 90 부근이다.** 지금 격차 10~14점의 정체는 문장력이 아니라 **측정되지 않은 숫자**다.

## 1. 심사위원은 이 보고서를 이렇게 읽는다

20페이지를 처음부터 정독하는 심사위원은 없다. 실제 순서는 이렇다.

```
표지 → P3(무엇을 만들었나) → P16(진짜 다 됐나) → P15(남들과 뭐가 다른가)
     → 여기서 인상이 80% 결정된다
     → 그 다음에야 P4~P13 을 의심하며 확인한다
```

### 지금 이 경로를 따라가면 무슨 일이 일어나는가

**P3 (개발 목표 및 시스템 구성)** — 좋다. 구성도가 신호 이름(`resp_rate_bpm`, `co2_ppm`, `thermal_max_c`, `pir_motion`, `valid{}`)까지 달고 있어서 "이 팀은 진짜 만들었구나"가 3초 안에 전달된다. **이 페이지는 건드리지 마라.**

단 한 가지, **소스코드와 시연동영상 칸이 비어 있다.** 심사위원이 가장 먼저 보는 페이지에 빈칸 두 개가 있으면 그 자체로 "미완성"이라는 첫인상이 박힌다. 이건 반드시 채워야 한다.

**P16 (구현 결과 및 검증 수준)** — 여기서 문제가 생긴다.

표 맨 아랫줄이 이렇다.

```
4센서 통합 HIL | 미착수 | 미검증 | 해당 없음 | 최우선 과제
```

정직한 표기이고, 나는 이 표기를 유지하라고 계속 주장해 왔다. **그런데 대상을 노린다면 이 줄이 남아 있으면 안 된다.**

이유는 도덕이 아니라 구조다. 심사위원 입장에서 "4센서 통합 HIL 미착수"는 이렇게 번역된다.

> "센서 4개를 하나로 합친 시스템이 실제로 동시에 돌아가는 걸 이 팀은 아직 못 봤다."

작품명이 **"밀폐공간·차량 생명감지 및 위험도 자동경보 시스템"**인데, 그 시스템이 통째로 돌아가는 증거가 없다는 뜻이 된다. 채널별 검증이 아무리 훌륭해도 이 한 줄이 전체를 "부품 모음"으로 격하시킨다.

**이건 글로 못 고친다. 통합을 끝내고 로그를 찍는 것 말고는 방법이 없다.** 지금 진행 중이라니, 이게 이 프로젝트의 승부처다.

**P15 (기존 방식 및 유사 사례 비교)** — 비교축은 잘 잡혔다. 그런데 마지막 줄에서 SafeNest 만 `×` 다(통합 실기기 검증 완료). 정직성 장치로 넣은 것이지만, **P16 과 겹쳐서 "미완성" 인상을 두 번 준다.** 통합이 끝나면 두 곳이 동시에 해소된다.

## 2. 배점별 냉정한 평가

### 독창성 30점 → 현재 23~24

**강한 것**
- fail-closed 판단 보류(`risk_score=None`)는 학생 프로젝트에서 거의 보이지 않는 발상이다. 대부분은 "센서가 죽으면 어떻게 되는가"를 아예 생각하지 않는다. **이건 진짜 차별점이다.**
- 유효성·신선도를 1급 상태로 관리하고 무효값을 `null` 로 보내는 설계. `formatNullableFloat()` 는 이 보고서에서 가장 설득력 있는 10줄이다.
- 재현 검증 실패 모델을 스스로 차단한 판단.

**깎이는 것**
- **차별점이 "안전 설계 철학"에 몰려 있고 "기능"에 없다.** 심사위원이 "그래서 이 장치가 뭘 더 잘하는데?"라고 물으면 답이 약하다. fail-closed 는 잘못될 때 안전한 것이지, 평소에 더 잘 감지하는 게 아니다.
- P15 선행 사례 3건은 넣었지만 **전부 정성 비교**다. Vayyar Care 는 낙상 3단계를 구분하고, arXiv 2403.05634 는 낙상 정확도 96.3%를 보고한다. **숫자를 가진 상대와 숫자 없이 비교하고 있다.** 심사위원 눈에는 SafeNest 가 불리하게 보인다.

**해야 할 일** → §4-3, §5-P15

### 기술성 및 완성도 30점 → 현재 21~23

**강한 것**
- 4개 센서를 UART/I²C/SPI/GPIO 4종 버스로 한 MCU 에 통합. 임베디드 난이도로 정당하다.
- SafeNest TCP v1 자체 프로토콜(16B 헤더, 길이 접두 프레이밍, network byte order). 직접 설계했다는 게 보인다.
- CRC-16/CCITT-FALSE + 헤더 범위 재계산 + 시퀀스 교차 확인 + 죽은 화소 배제 + 30초 무프레임 자동 복구. **무결성 방어가 5중이다. 이건 대회 수준을 넘는다.**
- `delay()` 미사용 + FreeRTOS 태스크 분리 + 1-slot 큐. 실시간 설계를 이해하고 있다.
- 열화상 실기기 E2E p50 162.70 / p95 173.90 ms 실측.

**깎이는 것 — 여기가 진짜 문제다**

1. **통합 시스템이 한 번도 관통되지 않았다.** (P16 마지막 줄)
2. **경보 지연이 측정된 적이 없다.** 초기 KPI 가 `경보 ≤ 2초` 였는데 보고서 어디에도 "센서 이상 발생 → 부저 울림"까지의 실측이 없다. **작품명에 "자동경보"가 들어가는데 경보 속도를 모른다.**
3. **가중치 0.35 / 0.35 / 0.15 / 0.15 에 근거가 없다.** P10 에 산식은 있는데 왜 그 숫자인지가 없다. 심사위원이 반드시 찌른다. "mmWave 와 CO₂ 가 왜 같은 0.35 입니까?"
4. **임베디드 대회인데 전력·발열·신뢰성 수치가 없다.** RAM 9.9% / Flash 20.5% 는 컴파일 타임 수치다. 심사위원이 기대하는 건 소비전류, 연속 가동 시간, 부팅 시간, **복구 시간**, 동작 온도다.
5. **AI 가 약하다.** ← 아래 별도

**해야 할 일** → §4-1, §4-2, §6

### 활용성 20점 → 현재 14~15

**강한 것**
- 밀폐공간이라는 1차 적용처가 구체적이고 법령(산안법 619조, 시행규칙 별표18)과 연결되어 있다.
- 확장 시나리오를 실측 감지거리(0.6·0.9 m presence 1.000, 1.2 m 0.814, 1.5 m lock loss)와 연결한 건 이 보고서에서 가장 영리한 부분이다. 정성 서술을 정량 근거로 바꿨다.
- QR 공간코드 3종이 실제 구현물이다.

**깎이는 것**
- **원가가 없다.** 부품은 다 샀는데 BOM 표가 없다. 활용성에서 가장 싸게 얻을 수 있는 점수를 버리고 있다.
- **현장 의견이 0건이다.** 밀폐공간 안전관리자, 지자체 맨홀 관리 부서, 소방 중 **단 한 곳의 의견도 없다.** "감시인 배치가 어렵다"는 주장이 전부 문헌 인용이다.
- 기대효과가 "~할 수 있다" 수준. 정량 목표가 없다.

**해야 할 일** → §6-5, §6-6

### 정보전달력 10점 → 현재 8.5~9

문체·레이아웃 정리는 끝났다. 명사형 제목 + 번호 체계, em dash 0건, 콜아웃 박스 4개로 정리, 본문 12pt 이상. **여기는 더 손댈 게 거의 없다.**

남은 감점 요인 하나 : **P3 의 빈칸 2개.**

### 팀 구성 및 역량 10점 → 현재 8~8.5

P20 구조(성명/구분/담당/CODEOWNERS/산출물)는 좋다. 기여도를 인위적으로 균등화하지 않은 것도 좋다.

깎이는 것 : **강유나 산출물 서술이 현재 저장소 상태와 어긋난다.** `RaspberryPi/Runtime/` 아래에 `gateway/`, `backend/app.py`, `services/`, `database/` 가 이미 병합되어 있고 FastAPI·SQLite·WebSocket 참조 파일이 각각 18·22·13개 있다. 보고서는 이걸 "정본 미병합"으로 보고 PIR·CAD·LCD 초기 골격으로만 축소해 놨다. **팀원 한 명의 기여가 실제보다 작게 적혀 있다.** 신규 저장소 이관 시 반드시 재검증할 것.

## 3. 대상을 막는 5대 병목

우선순위 순이다. 위에서부터 해결해야 아래가 의미를 갖는다.

### 병목 1 — 통합 시스템 관통 증거 (기술성 +4~6)

**증상** : P16 `4센서 통합 HIL = 미착수/미검증`, P15 마지막 행 SafeNest `×`

**왜 치명적인가** : 이 프로젝트가 "시스템"인지 "부품 모음"인지를 가르는 유일한 줄이다.

**필요한 것** (지금 통합 중이니 이 순서로)
1. 정본 `.ino` 를 ESP32 DevKit V1 에 플래시
2. Pi 에서 수신 서버 기동
3. `/health` 또는 `/api/state` 에서 **4채널 `valid` 가 동시에 true 인 상태를 60초 이상** 유지하며 로그 저장
4. 같은 구간의 ESP32 시리얼 로그도 저장
5. seq 연속성, 결측률, 1초 주기 유지 여부를 표로 정리

**보고서 반영** : P11 에 `④ 4센서 동시 수신 검증` 블록 신설, P16 마지막 행 갱신, P15 마지막 행 `×` → `○`

> ⚠ **로그 없이 이 줄을 바꾸지 마라.** 규정 제10조④ 위반이다. 통합이 끝나지 않으면 `미착수` 그대로 두는 게 맞다.

### 병목 2 — 경보 지연 실측 (기술성 +2~3, 독창성 +1)

**증상** : 작품명에 "자동경보"가 들어가는데 경보 속도가 보고서에 없다. 초기 KPI `≤2초` 도 미측정.

**왜 치명적인가** : 안전 시스템의 유일한 성능 지표는 "얼마나 빨리 알리는가"다. 이게 없으면 심사위원은 "구조는 좋은데 성능은 모르겠다"로 결론 낸다.

**측정 방법** (통합 완료 후 30분이면 된다)

```
방법 A (권장, 장비 불필요)
  스마트폰 슬로모션 240fps 로
  [센서 트리거 순간] ~ [부저 소리 시작 / LCD 등급 전환] 을 한 화면에 담아 촬영
  → 프레임 수 ÷ 240 = 지연(초). 10회 반복해 min/median/max 기록

방법 B (더 정확)
  Pi 에서 로그 타임스탬프로:
  패킷 수신 시각 → Risk 산출 완료 시각 → GPIO18 HIGH 시각
  세 구간을 분리 기록. 각 구간별 p50/p95 를 낸다.
```

**보고서 반영** : P10 또는 P11 에 한 줄. 예시 형식(숫자는 실측으로 채울 것)

```
경보 경로 지연 (n=10회)
  패킷 수신 → Risk 산출 : ___ ms (p50) / ___ ms (p95)
  Risk 산출 → 부저 출력 : ___ ms
  합계                  : ___ ms
  초기 목표 2,000 ms 대비 ___
```

**이 표 하나가 이 보고서에서 가장 강력한 단일 근거가 된다.** 초기 KPI 6개 중 유일하게 달성을 증명할 수 있는 항목이기도 하다.

### 병목 3 — AI 가 제목의 약속에 못 미친다 (기술성 +2~4, 독창성 +1~2)

**증상** : 작품명이 "**엣지 AI 기반**"인데 P9 를 보면
- 열화상 : 실기기 E2E ✅ (유일한 실물)
- CO₂ : 공개 데이터 오프라인만
- mmWave v0.1.0 : **배포 차단**
- mmWave v0.2.0 : 합성 468샘플 한정, 실센서 검증 불가

**적대적 심사위원의 질문** : *"모델 3개 중 2개가 못 쓰는 상태인데, 이게 AI 프로젝트입니까 아니면 규칙 기반 융합에 AI 를 붙인 겁니까?"*

이 질문에 지금 보고서는 답을 못 한다.

**두 갈래 중 하나를 선택해야 한다.**

**(A) 검증된 모델을 하나 더 만든다** ← 온디바이스 AI 작업 중이라니 이쪽
- 가장 현실적인 건 **CO₂ occupancy 모델을 실센서 데이터로 평가**하는 것이다. 이미 SCD40 실측 4세션(preflight 30 / baseline 300 / 호기 360 샘플)이 있다. 이 데이터에 라벨(재실/미재실)을 붙여 v0.1.0 모델을 돌리면 **실센서 기반 성능이 나온다.** 새 데이터 수집이 필요 없다.
- mmWave v0.2.0 은 합성 의존을 벗어나야 한다. `2026-08-01` 30분/31분 실측 로그가 있으니 이걸로 평가하면 "합성 한정" 딱지를 뗄 수 있다. **성능이 나쁘게 나와도 그 자체가 결과다.** 차단 판단의 일관성을 보여준다.

**(B) AI 기여의 정의를 바꾼다** (A 가 안 될 때의 차선)
- "우리는 좋은 분류기를 만들었다" → **"우리는 INT8 추론을 안전하게 만들었다"** 로 프레임을 옮긴다.
- 근거는 이미 있다 : full INT8 양자화(318KB), Pi 5 실기기 p95 173.90 ms, 유효 프레임 97.8%, **fail-closed 6종 실기기 PASS**, 검증 실패 모델 배포 차단 메커니즘.
- 이건 거짓이 아니고, 실제로 이 팀이 한 일이다. 그리고 학부 수준에서 드물다.

**어느 쪽이든 P9 제목을 바꿔라.**
현재 `3.4 온디바이스 AI 모델 구성과 검증 범위` → `3.4 온디바이스 AI 적용과 안전한 추론 설계` 같은 방향. 지금 제목은 "우리 모델 검증 못 했어요"를 스스로 광고한다.

### 병목 4 — 임베디드 신뢰성 수치 부재 (기술성 +2~3)

**임베디드SW경진대회**다. 심사위원 중 상당수가 하드웨어 사람이다. 그들이 찾는 숫자가 지금 하나도 없다.

측정해야 할 것 (전부 반나절이면 된다)

| 항목 | 측정 방법 | 왜 필요한가 |
|---|---|---|
| **복구 시간** | 열화상 케이블 분리 → 재연결 → 정상 프레임 복귀까지 초시계 | `recoverThermalIfStale()` 를 이미 구현했다. **동작을 증명만 하면 된다.** 가장 싸고 강력하다 |
| **소비 전류** | USB 전류계(수천 원) 를 ESP32 와 Pi 각각에 물림. idle / 정상 / 경보 3상태 | 밀폐공간 = 전원 확보 어려움. 배터리 운용 가능성 논거 |
| **연속 가동** | 통합 상태로 6~24시간 방치, seq 누락·재접속 횟수 집계 | 가용성 KPI(≥99%) 의 유일한 근거가 된다 |
| **부팅 시간** | 전원 인가 → 4채널 valid 까지 | 현장 재기동 시나리오 |
| **동작 온도** | 하우징 조립 상태 30분 연속 가동 후 표면온도 | 3D 출력 하우징 발열은 P18 에 "미검증"으로 남아 있다 |

**복구 시간 하나만 해도 좋다.** "센서 케이블을 뽑았다가 다시 꽂으면 __초 만에 자동으로 복구된다"는 문장은 무인 감시 장치의 핵심 주장이고, 지금은 코드만 있고 증거가 없다.

### 병목 5 — 가중치·임계값의 근거 (기술성 +1~2)

**증상** : `R = 100 × (0.35·mmWave + 0.35·CO₂ + 0.15·PIR + 0.15·Thermal)` — 왜 이 숫자인가?

CO₂ 1,500 ppm 은 실내공기질 관리법 시행규칙 별표2 근거를 이미 붙였다(잘했다). **가중치는 아직 맨몸이다.**

**가장 싼 해결책 : 민감도 분석.** 새 실험이 필요 없다.

```
기존 실측 로그를 입력으로 두고 가중치를 흔들어 본다.
  예: mmWave/CO₂ 를 0.25~0.45, PIR/Thermal 을 0.05~0.25 범위로 스윕
  각 조합에서 NORMAL/CAUTION/DANGER 판정이 얼마나 바뀌는지 집계

→ "판정이 가중치에 민감하지 않다" 가 나오면 그것 자체가 결과다.
→ "특정 구간에서 뒤집힌다" 가 나오면 그 구간을 밝히는 게 더 강한 결과다.
```

한나절이면 되고, P10 에 한 줄 표로 들어간다. 심사위원의 "왜 0.35 입니까"에 **"흔들어 봤는데 판정이 안 바뀝니다"** 라고 답하면 그 순간 기술적 신뢰가 올라간다.

## 4. 지금 진행 중인 작업으로 회수할 것

### 4-1. 4센서 통합 (진행 중) → 병목 1 + 2 동시 해결

통합이 끝나는 순간 **한 번의 세션으로 아래를 전부 확보**해야 한다. 따로 하면 두 번 고생한다.

```
[통합 완료 직후 1회 세션 체크리스트]
□ 4채널 valid 동시 true, 60초 이상 연속 로그 (JSON 저장)
□ 같은 구간 ESP32 시리얼 로그
□ seq 연속성 / 결측률 / 1초 주기 유지 여부
□ 경보 지연 10회 반복 측정 (슬로모션 or 로그 타임스탬프)
□ NORMAL → CAUTION → DANGER 전이를 실입력으로 재현, 각 전이 시점 기록
□ 센서 1개 물리적 분리 → DEGRADED 진입 확인 (가중치 재정규화 동작)
□ 센서 전부 분리 → FAILED, risk_score=None 확인  ★
□ 재연결 → 자동 복구 시간 측정
□ 위 전 과정 영상 촬영 (시연영상 소재로 그대로 쓴다)
```

★ 표시한 항목이 **이 프로젝트의 유일무이한 차별점을 실기기에서 증명하는 순간**이다. 놓치면 안 된다.

### 4-2. 시연영상 (편집 중) → 독창성 + 정보전달력

**대부분의 팀 영상은 잘 되는 장면만 보여준다. 그래서 다 똑같아 보인다.**

SafeNest 영상에 반드시 들어가야 할 컷 :

```
[컷 A] 정상 동작 — 사람이 들어가고 화면이 안전·재실로 바뀐다        (15초)
[컷 B] 위험 감지 — CO₂ 상승 또는 무움직임 → 주의 → 위험 → 부저      (30초)
[컷 C] ★ 센서 케이블을 뽑는다 → 화면이 '정상'으로 남지 않고
        '통신 오류 / 점검 필요'로 바뀐다                              (15초)
[컷 D] 다시 꽂는다 → 자동 복구                                        (10초)
```

**컷 C 가 이 영상의 승부처다.** 10초짜리 장면 하나로 "이 팀은 센서가 죽었을 때를 설계했다"가 증명된다. 다른 어떤 팀도 이 장면을 못 찍는다. 그들은 그 기능이 없기 때문이다.

편집 시 컷 C 에 자막을 넣어라 : **"센서가 멈춰도 '정상'으로 표시하지 않습니다"**

- 3분 이내, 720p 이상
- 유튜브 제목 : `2026ESWContest_자유공모_가만있어도SANDI_시연동영상`
- URL 확보 즉시 P3 에 삽입

### 4-3. 온디바이스 AI 완료 후 → 병목 3 해결

완료 시 P9 를 재구성한다. 반영할 것 :

## 10. 마지막으로 — 이 프로젝트가 가진 진짜 무기

객관적으로 보면, 이 팀에는 다른 팀에 없는 게 하나 있다.

**"센서를 믿을 수 없을 때 어떻게 할 것인가"를 설계 단계에서 정면으로 다뤘다는 것.**

- 무효값을 0 이 아니라 `null` 로 보낸다
- STALE 입력을 마지막 정상값으로 재사용하지 않는다
- 전 센서 무효면 위험도를 아예 산출하지 않는다 (`risk_score = None`)
- 재현 검증에 실패한 모델은 스스로 배포를 차단했다
- 실패한 측정(baseline 277/300, 결측 7.67%)을 지우지 않고 증거로 보존했다

이건 학부 프로젝트에서 거의 나오지 않는다. 대부분은 잘 되는 경로만 만들고 끝낸다.

**문제는 이 무기가 아직 "설계 문서 안에서만" 존재한다는 것이다.**

통합을 끝내고, 센서 케이블을 뽑았을 때 화면이 '정상'으로 남지 않는 장면을 실기기에서 찍는 순간, 이 프로젝트는 **"안전을 진지하게 다룬 팀"** 으로 기억된다. 그게 대상을 가르는 지점이다.

지금 필요한 건 새로운 아이디어가 아니라, **이미 만들어 둔 것을 증명하는 60초짜리 로그 하나**다.
